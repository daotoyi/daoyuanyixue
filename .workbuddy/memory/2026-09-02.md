## 上传"卡半天" + 重新上传不排队 (11:30, v1.11.309)
- **用户反馈**: 16课时控笔(弗、者)上传又卡死; 同时重新上传一个视频, 该视频立即开始上传, 排队机制形同虚设

  1. **卡死无自愈**: `storage.uploadFile` 只有 init 阶段(getStorage)有 15s 超时, **真正的上传阶段没有任何超时**。网络挂起/连接僵死时该 Promise 永不 settle → `currentUploadingEp` 被永久占用 → 队列永不前进("卡半天")

  3. **取消不释放通道**: `cancelEpisodeUpload` 不置空 `currentUploadingEp`, 导致 `dequeueNext` 的 `if (uploadQueue.length>0 && !currentUploadingEp)` 恒假 → 队列停摆; 且取消"排队中"课时不从 `uploadQueue` 移除 → 之后仍被出队上传

## 上传"永不放弃"改造 (13:00, v1.11.310)
- **用户新要求**: "可以慢, 但要求不能中断, 不能卡顿, 不退随意退出" —— 明确否决 v1.11.309 的"120s 无进度就自动跳过"(那本身就是一种中断/放弃)
- **关键认知**: 进度回调是 `onProgress(ratio, uploaded, size, {speedBps, etaSec, concurrency, partSize})`, 第 2 参是真实已传字节; 用整数 pct 判断"是否有进展"会误杀慢速上传(1GB 视频慢网下 1%=10MB 可能几分钟)
- **发现的真凶(SDK 硬退出点)**: `cloudbase.js uploadMultipartToCos` 虽号称"永不放弃", 但有多处直接 throw 终止整传:
  - **line ~402 补齐分片失败一次即 `throw`** → 整段上传前功尽弃(最主要"随意退出"来源)
  - `round > 16` 放弃; `verifyRounds >= 4` 放弃
  - 上层 `startUpload` catch 收到 throw 后还把 `ep._progress = 0` → 用户看到"上传中断"且进度清零
- **修复 v1.11.310**:
  1. **SDK 加心跳**: `emitProgress(isHeartbeat)` 上报时带 `heartbeat` 标记; 每 10s `setInterval` 报一次心跳(即使无分片完成), `finally` 里 `clearInterval(hbTimer)`。上层据此区分【在传但慢】vs【真卡死】, 慢速上传永不被误杀
  2. **SDK 去硬退出点**: 补齐失败不再 throw, 改为退避后续补(`sleep(2000*min(verifyRounds+1,5))`); `VERIFY_MAX_ROUNDS` 4→8; `round > 16` → `round > 40`
  3. **`startUpload` 永不放弃重试循环**: `while(true)` 包住 `storage.uploadFile`; 除 `control.userCancelled`/`control.yieldPause`/gen 过期外**任何失败都重试**(网络错误/分片失败/补齐失败/卡死), 退避 3/6/12/24s→30s 封顶; 每次重试用 `control.uploadId + partNumbers` 构造 `attemptResume` 从断点续传, **进度绝不清零**; 状态提示"网络较慢，自动续传中…（第 N 次）"
