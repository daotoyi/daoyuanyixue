## v1.11.268: 根治排队不出队 (竞态+对象引用双bug)
- **用户反馈**: 有2个排队任务但没有活跃上传，队列不自动出队
- **根因分析**:
  1. **竞态条件**: `dequeueNext` 是 async，先检查 `currentUploadingEp` 锁再 `await startUpload`，但锁在 `startUpload` 内部才设置 → 取消回调和 finally 同时触发 `dequeueNext` 时两个异步调用互相覆盖 → 队列卡死
  2. **对象引用过期**: 队列存的 ep 是旧 JavaScript 对象，关闭/重开弹窗后 `openCourseForm` 重建 episodes 数组(`map` 创建新对象)，队列里的 ep 指向不可见的旧对象 → 上传在后台跑但 UI 看不到
- **修复**:
  1. `_dequeueRunning` 同步锁 + `currentUploadingEp = ep` 提前到 `await startUpload` 之前 → 防竞态双保险
  2. `dequeueNext` 按 `_key` 映射到当前 `courseForm.episodes` 中的对象 → 防旧引用
  3. `removeFromQueue` 按 `_key` 匹配 → 防旧对象引用删不掉
  4. `startUpload` 入口防御: 若旧 `currentUploadingEp` 已不是上传中状态，清空避免死锁
  5. `dequeueNext` finally 中残留检测: 队列还有任务但无上传中时重新触发

## v1.11.269: 根治分片上传卡死在26% (AbortController 不万能 → 硬超时)
- **用户反馈**: 当前上传任务又卡死了，半天进度条不变化。书法艺术第一课时一直26%
- **根因 (关键教训)**: 代理/VPN 网络下单个分片 PUT 请求**挂起(hang)**而非失败，
  `setTimeout(() => controller.abort(), PUT_TIMEOUT_MS)` **不产生 reject** —
  fetch 在挂起态 abort 可能不触发 promise reject → 整批 `Promise.allSettled` 永不 settle
  → onProgress 不再被调用 → 进度永久冻结在某一百分比(26%)，且用户点取消/暂停也无反应
- **修复: 硬超时模式 (不依赖 abort 是否生效, 到点必定 reject)**
  1. **分片 PUT** (`uploadMultipartToCos` 内): 用 `Promise.race([fetch(...), 硬超时Promise])`
     在 `PUT_TIMEOUT_MS + 3000` (93s) 强制 reject(code=HARD_TIMEOUT) → 进入既有失败→重试轮次
  2. **`apiRequest` (云函数)**: 同样加 `Promise.race` 硬超时 `timeoutMs + 3000`，
     防护"取签名/listParts/completeMultipart"挂起拖垮整段上传
- **铁律**: **AbortController 在网络挂起(hang)场景下不保证 reject** —
  凡涉及网络的超时兜底，必须用 `Promise.race([请求, 定时reject])` 硬超时，不能只靠 abort
