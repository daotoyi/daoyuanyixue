## v1.11.281 修复大视频"合并分片失败: One or more of the specified parts could not be found"
- **报错复现**: 书法精品课45讲 第一课时上传, 上传中断后合并报 COS `part not found`
- **根因(两个)**: ①COS 分片列表最终一致性 — v1.11.280 把并发拉到8且"传完立即合并", 刚传完的分片可能还没被 listParts 看到 → multipartComplete 报 part not found; ②"PUT 返回200但未真正落盘 / 上传中断留半片" 进了 donePartNumbers, 云端实际没有, 服务端 listParts 过滤后静默丢掉 → 报缺失或生成缺片损坏文件
- **修复**:
  1. 云函数 `storageCompleteMultipart`: 改为重试循环(最多5次, 800/1600/3200/6400ms 退避), 每次重试重新 `multipartListPart` 取最新 ETag+PartNumber 再 complete; 仅对 `part not found`/`no such upload` 做可重试判定; 重试耗尽后诊断缺失分片号并明确报错(便于客户端定向重传)
  2. 客户端 `uploadMultipartToCos` 合并前新增"校验补齐"阶段: 以服务端 `storage.listParts` 为权威, 遍历 1..totalParts 找出云端缺失分片 → 重新批量签名 + `uploadOne` 补齐(最多4轮); 全部存在后才调 completeMultipart。杜绝"以为传完实则缺失"导致的 part not found 与缺片损坏
- **版本**: bump 280→281, commit 12e8f88, tag v1.11.281 -f 指向发布提交; gen-version v1.11.281 12e8f88
- **部署**: 云函数 dy-api 重部署(合并重试生效) ✅; H5 构建 upload /h5/ (82文件0失败) ✅; mp-weixin 构建 ✅; GitHub push main(12e8f88)+tag v1.11.281 ✅
- **结论**: 该报错为 v1.11.280 高并发+即时合并引入的一致性竞态, 非逻辑永久缺陷; 用户在 H5 后台刷新后重试即可(断点续传只补缺失分片)

## v1.11.282 修复"上传过程中自动断"(根因: 分片过大→长连接被掐断)
- **用户反馈**: 281 仍报"上传中断，合并分片失败"。定位: dashboard catch(3177) 给任何失败冠"上传中断："前缀, 故"合并分片失败"是合并阶段 part not found; 其根因是有分片根本没落到 COS
- **真正根因(自动断)**: v1.11.280 把分片放大到 32~128MB → 每个 PUT 是 30s~2min 长连接, 在手机/WiFi/代理/NAT 空闲超时下极易被中间设备掐断; 长连接一断该片丢失 → 合并时云端缺片 → part not found
- **修复(抖音/视频号/小红书同款小分片)**: `pickPartSize` 反转为**默认 4MB 小分片**(长连接仅数秒, 几乎不被掐断; 单分片失败仅丢 4MB 秒级补齐); 仅当文件 >40GB 逼近 COS 10000 片上限才按需翻倍放大。同步更新顶部说明, 防后人改回"越大越好"
- **关键提示**: 281 已含合并前"校验补齐"块(listParts 为权威补齐缺失分片)+ 云函数 complete 重试兜底; 用户 281 仍报错高度疑似**H5 静态资源被浏览器缓存**(跑的是旧 280 包, 无校验块)。故 282 必须**硬刷新(Cmd/Ctrl+Shift+R)**绕过缓存才生效
- **版本**: bump 281→282, commit 271b70c, tag v1.11.282 -f 指向发布提交; gen-version v1.11.282 271b70c
